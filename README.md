## 3. Ответы на контрольные вопросы

### 1. Почему одноэтапная сборка не подходит для продакшна?
Одноэтапная сборка оставляет в итоговом образе все исходные файлы данных (`data/records.csv`), инструментарий для генерации отчетов (`tools/`) и исходный код тестов (`tests/`). Это сильно увеличивает размер образа, засоряет окружение лишними зависимостями и создаёт риски безопасности (утечка исходных данных и тестов в продакшн).

### 2. Зачем нужен multi-stage build и как он помог в этой работе?
Multi-stage build позволяет разделить процесс сборки на промежуточные стадии (`build`, `test`) и финальную стадию запускного образа. В нашем случае стадия `build` сгенерировала `report.json`, стадия `test` прогнала тесты `unittest`, а в финальный образ попал **только готовый `report.json`** и лёгкий скрипт `app/server.py`. Это позволило исключить исходный `records.csv` и тесты из финального образа.

### 3. Как Docker использует кэш слоев и что произошло при изменении `records.csv`?
Docker кэширует каждый слой `Dockerfile` последовательно. Если содержимое одного из файлов (или инструкция) меняется, кэш для этого слоя **инвалидируется**, а также автоматически пересобираются все последующие слои в этой стадии. 
В нашем эксперименте с `records.csv`:
* Шаги `COPY tools/` и базовый образ взялись из `CACHED`.
* Шаг `COPY data/` вызвался заново, так как файл `records.csv` изменился.
* Все последующие шаги стадий `build` и `test` (генерация отчёта, запуск `unittest`) выполнились заново (`DONE`).

### 4. Зачем выносить веб-интерфейс в отдельный контейнер с Nginx?
Разделение API и Web соблюдает принцип **Single Responsibility** (один контейнер — одна задача). Nginx высокоэффективен при отдаче статики (HTML/JS/CSS) и проксировании запросов, а API занимается исключительно бизнес-логикой. Это позволяет масштабировать или обновлять веб-интерфейс и бэкенд независимо друг от друга.

### 5. Для чего нужна пользовательская сеть Docker (`medeu-net`)?
Пользовательская bridge-сеть обеспечивает:
1. **Внутренний Встроенный DNS:** контейнеры могут обращаться друг к другу по имени сервиса (`http://medeu-api:8080`), а не по динамическим IP-адресам.
2. **Изоляцию и безопасность:** контейнеры в общей сети могут взаимодействовать напрямую, не выставляя наружу лишние порты.

## 4. Возникшие трудности и их решения
* **Соблюдение порядка слоёв:** Важно копировать сначала редко меняющиеся файлы (`tools/`), а затем частые (`data/` и `app/server.py`), чтобы кэш Docker использовался максимально эффективно.
* **Связка контейнеров в сети:** Настройка Nginx требовала точного указания хоста `medeu-api` в файле `nginx.conf` для корректного проксирования `/api/`.
